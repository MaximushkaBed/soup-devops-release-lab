The original four incidents demonstrate why source tests cannot validate a release. To make
this relevant to Soup's post-training work, I added an independently written LoRA/SwiGLU fixture
that checks derivatives and two optimizer steps, with two pinned PyTorch/Triton stacks. Four
training faults pass naive forward tests but fail installed-wheel and rebuilt-sdist contracts
for precise expected causes. This fixture illustrates a release-gate pattern; it does not
claim to test Soup's production kernels or full training dependency stack.

The most surprising result was that a correct forward pass can coexist with broken training.
Zero-initialized LoRA B also makes a zero first-step A gradient an easy false alarm. My remaining
concern is the workflow's trust boundary: a compromised maintainer can change code and checks.

Codex assisted with implementation, documentation and automated verification. I independently
configured TestPyPI's Trusted Publisher, installed the published 0.9.3 baseline in a fresh venv,
